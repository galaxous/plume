# Status Note - 2026-03-24

## Summary

This note records Plume's real readiness status as of 2026-03-24.
It was written especially to clarify, for `native` and `laradock-bridge` modes, which command surfaces exist, which are at real runtime orchestration level, and which are still missing.

## Global Status

| Area | Status | Note |
|---|---|---|
| CLI/router/core | ready | phases 1-3 completed |
| Site registry/onboarding | ready | central registry + prompt + publish/reload flow exists |
| Multi-webserver config generation | ready | `nginx`, `apache2`, `caddy` snippet parity exists |
| Native mode | partial | command surface exists; real OS package/service-manager integration is missing |
| Laradock bridge mode | partial | bootstrap + strict preflight exists; full bridge lifecycle does not |
| Docker-lite mode | beta-frozen | not the active development focus |

## Native Mode Readiness

### Working

- `services supported/status/health/logs/up/down/install/update` command surface exists.
- Service support matrix is defined:
  - `php`
  - `composer`
  - `nginx|apache2|caddy`
  - `mariadb|mysql`
  - `redis`
  - `phpmyadmin`
  - `postgres`
  - `memcached`
  - `rabbitmq`
  - `mongodb|mongo-webui`
  - `mailpit`
  - `meilisearch`
  - `minio`
  - `supervisor`
  - `horizon`
  - `php-worker`
- Port intelligence exists:
  - if the default port is taken, a fallback port is selected
  - written to the state file and SQLite state DB
- Version and alias behavior exists:
  - PHP alias resolution
  - custom version metadata
- Toggle-aware reconcile exists:
  - `false -> true` transitions can be detected via `services update`
- Dependency guard exists:
  - `horizon -> supervisor`
  - `phpmyadmin -> PMA_DB_ENGINE + selected db service`
- Site onboarding is one of the most mature native areas:
  - `site add/list/check/update/publish/remove`
  - custom server config
  - per-site php upstream selection

### Missing Today

- The native `install/up/down` flow does not yet complete real package manager and service manager integration.
- So today's native behavior is:
  - a state/log/port-focused orchestration model
  - fail-fast validation
  - but not yet full `brew/apt/dnf + launchd/systemd/service` provisioning
- The `workspace` concept in native mode is not at Laradock-like real runtime shell/tooling experience level.
- `redis-webui` native parity implementation does not exist yet.
- Production-grade rollback, secrets, TLS, monitoring, and backup scopes are in the phase 9+ area.

### Conclusion

Native mode today is at a "good control plane + stateful orchestration surface" level.
It has not yet reached the target Herd-like "production-usable runtime that installs and manages real host services with a single command" level.

## Laradock-Bridge Readiness

### Working

- `services laradock init`
- `services laradock sync`
- `services laradock check`
- `laradock-bridge` context management via `mode path set/get/use`
- Strict Laradock preflight:
  - is the compose file present
  - are required services defined
  - is `.env` present
  - is `APP_CODE_PATH_CONTAINER=/var/www`
  - is `APP_CODE_PATH_HOST` resolved
  - are registered site paths inside the host scope
- Laradock strict path/compose/container guard exists on the site publish/reload side

### Missing Today

- Full service lifecycle parity for Laradock-bridge is not there yet:
  - `services up/down/status/health/logs` commands are not at the same maturity as native
- Bridge sync that normalizes live Docker container state into the state DB is missing
- Full adapter contract is missing:
  - same command as native, different engine logic is not finished yet
- Safe interoperability exists as a first step, but no-destructive runtime mapping is incomplete
- Laradock strict path/project rules exist at bootstrap level; real operations and drift tracking layers are missing

### Conclusion

Laradock-bridge today is at a "bootstrap + validation + strict boundary guard" level.
It has not yet reached the target "manage the existing Laradock stack with plume as one system" level.

## Site Layer Readiness

This layer is the most mature area across the project.

- Central site registry exists
- Mode-aware cache/snippet generation exists
- `nginx|apache2|caddy` parity exists
- `--server-config` override exists
- per-site php selection exists
- laradock strict preflight publish/reload guard exists

Therefore, while the services/orchestration side evolves in later steps, the site layer can again be used as the baseline reference.

## Immediate Priority After This Note

1. Real `up/down/status/health/logs/exec/containers` parity for Laradock-bridge must be completed.
2. The same adapter contract should be applied to native mode and real host service manager integration should start.
3. The Laravel runtime piece for native mode must be completed:
   - `workspace`
   - `php-worker`
   - `horizon + supervisor`
   - `phpmyadmin`
   - `redis-webui`

## Guardrail

After this note, no new thread or implementation should assume:

- native mode fully performs real host provisioning
- laradock-bridge manages the runtime lifecycle with full parity

The correct assumption is:

- native = command surface + state orchestration ready, real provisioning incomplete
- laradock-bridge = bootstrap/preflight ready, runtime bridge incomplete
